# Running PostgreSQL locally

Covers the Phase-1 persistence foundation ([ADR 0002](adr/0002-postgres-pgvector.md)):
`source_items` and `document_snapshots` only. No pgvector, no other tables yet.

## 1. Start PostgreSQL

```bash
make db-up
```

Starts the `postgres:17` container defined in `compose.yaml` and waits for its health
check to pass. Data persists in the `ai-daily-digest-postgres-data` Docker volume across
restarts; `make db-down` stops the container without deleting that volume.

## 2. Point the app at it

Copy `.env.example` to `.env` if you have not already, and set:

```
DATABASE_URL=postgresql+psycopg://ai_daily_digest:ai_daily_digest@localhost:5432/ai_daily_digest
```

This matches `compose.yaml`'s own local-only credentials — never a production secret.
`make db-migrate`, `make db-revision`, and `make test-integration` also read
`DATABASE_URL` from your shell environment; if it is unset they fall back to this exact
same local default (see the `Makefile`), so exporting it in `.env` is a convenience, not
a requirement, for local work.

## 3. Run the migration

```bash
make db-migrate
```

Runs `alembic upgrade head`, creating `source_items`, `document_snapshots`, their
constraints and indexes, and the Phase-1 immutability triggers (ADR 0002 section 11).

To create a new migration later (module owners only — see `AGENTS.md`'s database
review rule):

```bash
make db-revision message="add whatever table"
```

Alembic migrations in this project are **hand-written**, not autogenerated (ADR 0002
section 16) — `alembic revision` without `--autogenerate` gives you an empty template to
fill in yourself; do not add `--autogenerate` without checking the ADR's stated reasons
first (`text[]` columns and trigger DDL are not reliably autogenerated).

## 4. Run the integration tests

```bash
make test-integration
```

Runs `pytest -m integration` — every test under `tests/integration/`. Each test run
creates its own temporary, uniquely-named database (`ai_daily_digest_test_<random>`),
migrates it, runs, and drops it afterward; it never touches whatever database
`DATABASE_URL` already points to beyond using it as the connection template. Real
PostgreSQL only — never SQLite (arrays, native `uuid`, `timestamptz` precision, `ON
CONFLICT`, and row-level triggers are not faithfully reproduced by SQLite).

**If `DATABASE_URL` is not set**, integration tests skip individually with a clear
reason. If you explicitly pass `-m integration` (as `make test-integration` does) with
no `DATABASE_URL` reachable, the run fails loudly at collection instead of silently
skipping everything — that is deliberate (ADR 0002 section 15).

## 5. Everyday inner loop

`make check` (ruff, mypy, unit tests) never touches the database — it explicitly
excludes `-m integration` (`Makefile`'s `unit` target) and stays fast. `make ci` (the
full local approximation of the CI `tests` job) runs `-m "not live"`, which **does**
include integration tests, so it needs `DATABASE_URL` set and reachable; run `make db-up`
first, or set `DATABASE_URL` to skip integration tests individually if you only want the
unit suite.

## Troubleshooting

- **"set DATABASE_URL to run PostgreSQL integration tests" (skipped, not failed)**: no
  `DATABASE_URL` in your environment. Run `make db-up`, export `DATABASE_URL` (step 2
  above), and retry.
- **`make db-up` hangs waiting for "healthy"**: check `docker compose logs postgres`; a
  stale volume from an incompatible previous PostgreSQL major version is the most common
  cause — `docker compose down -v` removes the volume (destroys local data) if so.
- **CI**: the `tests` job in `.github/workflows/ci.yml` runs its own `postgres:17`
  service container automatically — no local setup is needed for CI to run the
  integration suite; the job fails outright if that service cannot become healthy.
